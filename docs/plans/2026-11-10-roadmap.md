# opsdesk roadmap

Each phase is one branch and has its own detailed plan (`docs/plans/<date>-phase-N-<name>.md`). Plans 6 to 8 were written ahead (2026-11-10, owner request) for Sonnet implementers; each starts with a prerequisite check against the merged code of the phases before it. Decisions: `docs/adr/0001-initial-decisions.md`. Skill coverage: `docs/context/skills-matrix.md`.

| # | Branch | Goal | Done when |
|---|---|---|---|
| 1 | `feature/foundation` | Maven multi-module, backend (catalog + incidents on PostgreSQL), Angular shell in one jar, TestNG | `./mvnw verify` green; `java -jar` serves UI + API against compose Postgres |
| 2 | `feature/ci-container` | GitHub Actions (build, test, JaCoCo, SonarCloud, Trivy fs + image, gitleaks secret scan on every push + documented pre-commit hook), multi-stage Dockerfile (non-root, arbitrary UID), image to GHCR, Dependabot, context check in CI | PR pipeline green; image in GHCR; Trivy without HIGH/CRITICAL |
| 3 | `feature/openshift-deploy` | Helm chart (Deployment, Service, Route/Ingress switch, probes, NetworkPolicy, Postgres secret ref), values per stage; CI: `helm lint` + `helm template` always, `oc login` + `helm upgrade --install` + smoke test when OpenShift secrets exist | lint/template green; deploy job skipped cleanly without secrets; works against a Developer Sandbox if the owner sets one up |
| 4 | `feature/observability` | Micrometer business metrics (incidents opened, open incidents gauge, time to resolve), Prometheus endpoint, ECS JSON logs, Datadog registry (profile `datadog`, off), Terraform for Datadog monitors + dashboard (`validate` in CI) | metrics visible on `/actuator/prometheus`; `terraform validate` green |
| 5 | `feature/mcp-server` | MCP server at `/mcp` (stateless Streamable HTTP, bearer token); tools `list_services`, `get_service_status`, `list_active_incidents`, `get_incident`, `open_incident`, `change_incident_state`; `.mcp.json`; `tools/mcp-verify.sh`; tool tests | MCP Inspector lists and calls tools; Claude Code can use it |
| 6 | `feature/runbook-rag` | `ai` module: runbook index + retriever, `LlmClient` (mock default), Azure OpenAI + AI Search adapters (profile `azure`, off), Terraform Azure (validate only), `/api/assist`, MCP tool `search_runbooks`, 3 to 5 runbooks | assist answers with sources from mock; Azure adapters compile and are marked MOCK |
| 7 | `feature/project-guide` | Frontend: **starts with a UI/UX analysis** (skill `ui-ux-pro-max`: layout, navigation, accessibility, visual language; findings drive the views; owner request 2026-11-10), then dashboard views + project guide/glossary (see below); static demo build for GitHub Pages | Pages site clickable without a backend |
| 8 | `update/templates-and-polish` | GitLab shared template + consumer, Jenkinsfile, Ansible playbook + Tower template (mocked), runbooks + postmortem template, README with "what this shows" table and diagram | every mock listed in README; context files current |

Phases 2 to 4 can swap order; 5 needs 1; 6 needs 5 for the MCP tool.

## Frontend (phase 7, decided by the owner 2026-11-10)
Keep the working dashboard (services, incidents, ask-the-runbooks) **and** add a "Project guide" area: architecture tour, "what this shows" per skill with links into the repo, glossary (MTTR, SLO, RAG, MCP, Helm, Route, ...) with a source link per term. Guide content lives as Markdown in `docs/guide/` so README and app share one source. A static build with an in-memory API mock goes to GitHub Pages, so a recruiter can click through without running anything.
